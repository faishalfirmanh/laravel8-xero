## 4. FASE AUDIT (urut)

### Fase 0 — Peta project (maks. ~15 tool call)
- `composer.json` / `composer.lock`: versi PHP yang diizinkan, versi `laravel/framework`, paket auth
  (sanctum/passport/jwt), paket upload/PDF/image/excel, dan paket yang sudah usang atau punya CVE yang kamu ketahui.
- `routes/api.php`, `routes/web.php`, `app/Http/Kernel.php`, `app/Providers/RouteServiceProvider.php`:
  peta route → middleware → controller. Tandai route TANPA auth, TANPA throttle.
- Ada tidaknya `Dockerfile`, `docker-compose*`, `.htaccess`, konfigurasi nginx/apache, `.env.example`,
  file deploy/CI di dalam scope (untuk menyimpulkan runtime PHP dan SAPI).

### Fase 1 — Isu PHP2Shell (CVE-2026-109618 & CVE-2026-109619)
Konteks (verifikasi ulang ke advisory resmi php.net bila punya akses; jangan berasumsi di luar ini):
- Ini cacat di **runtime PHP**, bukan di kode aplikasi. Aplikasi yang kodenya aman tetap terdampak.
  Middleware Laravel (termasuk `XssSanitization` dan `Authenticate`) **tidak bisa** memitigasinya,
  karena eksploitasi terjadi pada penanganan request di level PHP sebelum/di luar logika aplikasi.
- Semua SAPI yang melayani web terdampak: PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, LiteSpeed.
  mod_php dinilai paling berisiko.
- Perbaikan resmi: PHP 8.2.35, 8.3.36, 8.4.27, 8.5.12. PHP ≤ 8.1 tidak punya rilis resmi.
  Untuk PHP 7.4 / 8.0 / 8.1 tim keamanan PHP menerbitkan **backport source minimal** (harus compile sendiri / tunggu vendor).
- `RLIMIT_AS` / `RLIMIT_DATA` BUKAN mitigasi (justru bisa memicu jalur yang sama).
- Mitigasi tambahan (bukan pengganti patch): aturan WAF untuk vektor yang sudah dikenal (mis. Cloudflare),
  pembatasan/validasi multipart di reverse proxy, dan extension komunitas penutup jalur multipart (evaluasi risikonya sebelum dipakai).

Yang harus kamu lakukan (hanya dari file di dalam scope):
1. Simpulkan versi PHP & SAPI dari `composer.json` (`require.php`, `config.platform`), Dockerfile/base image tag,
   `.htaccess` (`AddHandler`/`php_value`/`php_flag` → indikasi mod_php), file deploy/CI.
2. Cari endpoint yang menerima `multipart/form-data` / upload file (route + controller + `$request->file`,
   `move`, `store`, `Storage::put`), dan upload tanpa auth. Ini permukaan serangan yang paling relevan untuk
   ditandai prioritas penanganan (WAF/limit ukuran di proxy) selama PHP belum dipatch.
3. Cari indikator kompromi statis (RCE berarti webshell): file `.php` di `public/` selain `index.php`,
   `eval(`, `assert(`, `base64_decode(` + `eval`, `gzinflate(`, `str_rot13(`, `preg_replace('/e'`,
   `system(`, `shell_exec(`, `passthru(`, `proc_open(`, `popen(`, `` ` ` `` di folder upload/public,
   `.htaccess` aneh di folder upload. Laporkan hanya path + alasan.
4. Di bagian laporan "Langkah Verifikasi Manual (di server, oleh admin)" cantumkan perintah yang
   HARUS dijalankan manusia (jangan kamu jalankan, karena di luar scope):
   `php -v`, `php -m`, `php-fpm -v` / `php-fpm8.x -v`, `apachectl -M | grep -i php`,
   `php -i | grep -i "Server API"`, dan cek PHP binary yang dipakai web (bukan hanya CLI).
5. Rekomendasi jalur realistis untuk project Laravel 8 ini (nilai sendiri kelayakannya dari composer.lock):
   (a) darurat: pasang backport PHP 7.4 resmi dari tim PHP + WAF + batasi upload; restart PHP-FPM/Apache/worker/queue;
   (b) jangka pendek: naikkan runtime ke PHP 8.3/8.4 (8.2 EOL 31 Des 2026) — nilai dulu kompatibilitas Laravel 8;
   (c) jangka menengah: upgrade Laravel 8 (sudah EOL) bertahap ke versi yang didukung.
   Tulis estimasi risiko & usaha masing-masing dalam 1–2 baris.

### Fase 2 — Analisis `XssSanitization` & `Authenticate` (inti permintaan)
Cari di `app/Http/Middleware/`, `Kernel.php`, dan `routes/*`.

**XssSanitization** — periksa dan jawab konkret:
- Teknik apa yang dipakai (`strip_tags`, regex, `htmlspecialchars`, library seperti HTMLPurifier)?
- Apakah dijalankan pada input sebelum disimpan (rawan merusak data & mudah di-bypass) atau escaping di output?
- Apakah mencakup JSON body, nested array, header, query, file name? Apakah mengubah tipe data (int/bool/null jadi string)?
- Apakah ada field yang sengaja butuh HTML (rich text) dan bagaimana ditangani?
- Apakah middleware ini dianggap sebagai satu-satunya pertahanan (anti-pola)? Apakah memberi rasa aman palsu
  terhadap SQLi, mass assignment, path traversal, SSRF, command injection (yang TIDAK ditangani XSS filter)?
- Apakah middleware ini dipasang di semua grup yang relevan, atau ada route yang lolos?

**Authenticate** — periksa dan jawab konkret:
- Guard & driver yang dipakai (session/token/sanctum/passport/jwt). Apakah `redirectTo`/respon untuk API benar (401 JSON, bukan redirect)?
- Apakah SEMUA route sensitif berada di grup `auth`? Daftar route yang lolos.
- Pengelolaan token: masa berlaku/expiry, rotasi, revoke saat logout/ganti password, penyimpanan di DB (hash atau plaintext),
  token di query string (bocor di log), kekuatan secret JWT, algoritma (`none`/HS256 lemah).
- Otorisasi, bukan hanya autentikasi: cek **IDOR/BOLA** (query berdasarkan `id` dari request tanpa filter kepemilikan),
  penggunaan Policy/Gate/`authorize()`, role/permission check di controller, **BFLA** (endpoint admin yang hanya mengandalkan "sudah login").
- `throttle` pada login/reset/OTP/register; enumerasi user lewat pesan error; `remember_me`; session fixation.

### Fase 3 — Kerentanan aplikasi (OWASP API Top 10 + Laravel spesifik)
Cari dengan grep terarah, lalu baca hanya konteks sekitar hit:
- **Injeksi**: `DB::raw`, `whereRaw`, `selectRaw`, `orderByRaw`, `DB::select/statement/unprepared` dengan interpolasi/concat;
  `orderBy($request->...)` / nama kolom dinamis; `exec`, `shell_exec`, `system`, `passthru`, `proc_open`, backtick; `eval`; `unserialize`; `include/require` dinamis.
- **Mass assignment**: `$guarded = []`, `$fillable` berlebihan (role, is_admin, balance), `Model::create($request->all())`, `->update($request->all())`, `forceFill`.
- **Upload**: validasi MIME/ekstensi/ukuran, nama file dari user, simpan di `public/` yang bisa dieksekusi, path traversal, SVG/HTML upload, `getClientOriginalExtension` dipercaya mentah.
- **Path traversal / file**: `Storage::download`, `response()->file`, `file_get_contents`, `readfile`, `fopen` dengan input user.
- **SSRF / open redirect**: `Http::get`, `curl_*`, `file_get_contents(url)`, `redirect($request->...)`.
- **Deserialisasi & object**: `unserialize`, `Crypt::decrypt` dari input, cookie/session driver, `APP_KEY` yang bocor/terkomit.
- **Konfigurasi**: `APP_DEBUG`, `APP_ENV`, `APP_KEY`, `.env` yang terkomit/terekspos, `config/cors.php` (`*` + credentials),
  `config/session.php` (secure/httponly/samesite), `config/logging.php` (log berisi data sensitif), `TrustProxies`, `VerifyCsrfToken` `$except`.
- **Rute berbahaya**: route debug/telescope/horizon/log-viewer/phpinfo/`artisan` via web yang tidak diproteksi.
- **Data**: password hashing (`bcrypt`/`Hash`, bukan `md5/sha1`), data sensitif di response API (over-exposure: `User::all()`, tanpa `$hidden`/API Resource),
  paginasi tanpa batas (DoS), validasi input yang hilang (tidak pakai FormRequest/`validate`).
- **Header & transport**: security headers (CSP, X-Content-Type-Options, HSTS, Referrer-Policy), force HTTPS.
- **Dependensi**: dari `composer.lock`, sebut paket dengan versi lama/EOL/abandoned yang kamu YAKIN rentan (sebutkan CVE hanya jika kamu yakin; jika ragu, tandai "perlu dicek dengan `composer audit`").
  `composer audit` butuh jaringan: jangan dijalankan, masukkan ke "Langkah Verifikasi Manual".

## 5. FORMAT OUTPUT — tulis ke `report_security.txt`
Teks polos (plain text), rapi, tanpa markdown berat. Urutan bagian:

```
LAPORAN KEAMANAN — laravel8-xero (Laravel 8 / PHP 7.4)
Tanggal: <hari ini> | Mode: read-only static review | Scope: /working/annamiro/laravel8-xero

1. RINGKASAN EKSEKUTIF
   - Skor risiko keseluruhan (Kritis/Tinggi/Sedang/Rendah) + 5 baris alasan utama
   - Jumlah temuan per severity
   - 3 tindakan yang harus dilakukan PALING DULU

2. ASSESSMENT PHP2Shell
   - Versi/SAPI hasil simpulan + tingkat keyakinan
   - Permukaan serangan (endpoint multipart/upload, tanpa auth)
   - Indikator kompromi statis (jika ada)
   - Rekomendasi darurat / jangka pendek / jangka menengah

3. ANALISIS MIDDLEWARE
   3.1 XssSanitization: cara kerja, kelemahan, bypass yang mungkin, saran realistis
   3.2 Authenticate: cara kerja, route yang lolos, kelemahan token, saran realistis
   3.3 Arsitektur pengganti yang disarankan (berlapis): validasi FormRequest, Policy/Gate,
       escape saat output, API Resource + $hidden, throttle, CSP — hindari "satu filter untuk semua"

4. DAFTAR TEMUAN (urut severity)
   Untuk tiap temuan:
   [ID] Judul — Severity (CVSS perkiraan) — CWE/OWASP
   Lokasi : path:baris (daftar lokasi jika banyak)
   Bukti  : 1 baris kutipan (rahasia disamarkan)
   Dampak : 1–2 kalimat
   Perbaikan: langkah konkret + contoh kode MAKSIMAL 8 baris
   Usaha  : Rendah/Sedang/Tinggi

5. ROADMAP PERBAIKAN
   P0 (hari ini–3 hari) | P1 (minggu ini) | P2 (bulan ini) | P3 (jangka panjang)
   Tiap butir mengacu ke ID temuan.

6. YANG SUDAH BAIK (singkat, agar tidak dikerjakan ulang)

7. TIDAK TERVERIFIKASI & LANGKAH VERIFIKASI MANUAL (di server, oleh admin)
   Perintah + tujuan masing-masing.
```
Aturan konten laporan:
- Setiap klaim wajib punya `path:baris`. Jika tidak ada bukti, taruh di bagian 7, jangan dikarang.
- Bedakan jelas: **terkonfirmasi** vs **dugaan**.
- Prioritaskan perbaikan yang realistis untuk tim kecil: perubahan kecil berdampak besar dulu.
- Tidak perlu mengulang isi prompt ini di laporan.
